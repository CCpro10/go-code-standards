# Review 问题复核与务实工程判断

**在修改前，先证明这个问题值得修改。** 工程设计是在正确性、可靠性、复杂度、性能和维护成本之间做权衡。允许经过评估、可接受的非关键失败；不能忽视破坏核心业务不变量的真实风险。

## 输入与复核

1. 获取已有问题列表、对应仓库和代码版本。保留问题编号，核对当前代码是否已变化或问题已修复；没有问题列表时先索取，不另开一轮泛化找 Bug。
2. 独立阅读相关实现、完整调用链、业务约束与实际运行条件。原 Review 和静态扫描都是待验证的主张，不能因为标了 P1 就认定成立。给出文件/行号、契约、测试或运行证据；缺少证据时说明缺什么。
3. 区分确定性 Bug、条件性现实风险、极端边界、合理设计取舍和纯理论可能性。构造不符合真实契约的输入、调用顺序或部署条件，不足以证明线上可触发。
4. 评估触发概率、影响范围、后果、可恢复性和业务重要性；无数据时不要编造概率。数据丢失、资金损失、安全漏洞、权限越界和严重并发一致性问题，即使低概率也要认真核实和处理。没有事故记录不等于安全。
5. 比较修复收益与新增分支、状态、副本、锁、重试、异步协调和兼容逻辑的成本。优先利用已有系统保证、业务不变量和基础设施；新增代码本身也可能引入 Bug。允许直接返回明确错误，不自动增加层层兜底。
6. 给出是否修复的明确决策。问题成立不代表一定值得修；复杂度明显超过收益时可建议暂不修复。值得修的问题选择满足业务要求的最简单方案，覆盖真实根因，不以代码行数少代替方案正确。

## 一致性与失败边界

- 先确认业务要求的是原子性、幂等性、顺序、最终收敛，还是允许短暂延迟；不能看到两个写入就要求加锁、事务或补偿队列。
- 若依赖重试、补查或人工恢复，核实机制确实存在、覆盖什么失败窗口及如何终止；不能凭“最终会一致”接受永久丢失或无限等待。
- 非核心路径偶发失败、外部依赖异常或可接受的短暂不可用，可以保留为显式失败。已确认的核心不变量破坏不能用“概率低”忽略。
- 风格和设计意见按明确规范与可读性收益判断，通常可直接给出简单建议；不把个人偏好包装成 Bug，也不因为它是风格修改就忽略改动成本。
- 不为证明 Review 有价值而强行修复，也不为减少工作而否定风险。高影响问题证据不足时列为优先核实，不能直接标为无需修复。

## 每项输出

- **问题是否成立**：确定存在 / 条件成立 / 证据不足 / 不成立；附关键证据或缺失证据。
- **触发条件**：真实需要满足的条件，以及现有保证是否阻止它发生。
- **实际影响**：概率依据、影响范围、核心业务后果与可恢复性。
- **修复成本**：新增复杂度、维护负担和可能引入的回归。
- **最终建议**：必须修复 / 建议修复 / 暂不修复 / 无需修复，并解释理由。
- **最小必要方案**：仅对值得修复的问题给出简单、足够可靠的方案和针对性验证；暂不修复时说明重新评估的触发条件。

最后汇总修复清单、接受的风险及待核实项。默认只复核；用户明确要求修复后，才执行已判定值得修的问题并验证。此 Skill 接收六个专项或人工 Review 的结果，不作为 review-coordinator 的第七个并行找问题专项。
