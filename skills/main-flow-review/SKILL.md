# 主链路与分层 Review

## 第一原则：代码像一本可逐层阅读的书

上层像目录，说明完整流程；下层像章节，自然展开已知步骤。每深入一层增加细节和理解价值。开发者应能在任意一层停下来，解释该层完整职责、主要步骤与控制关系。

## 检查

- 从受影响入口梳理真实调用链：目标、准备、执行、收尾、数据输入输出、关键分支和副作用。
- 上层不必暴露实现细节，但必须看得见业务步骤与执行顺序；下层不能突然引入名字未表达的新业务阶段。
- 同层保持相近抽象粒度，避免业务编排 → 底层操作 → 业务编排反复跳跃。
- 按自然业务职责组织流程。检查在线正常路径是否被回放、评测、后台处理等独立场景的编排侵入。
- 参数校验和失败快速返回，保持正常路径顺序清晰；重试、回滚、取消、并发与汇合的位置应可追踪。
- 区分调用深度、分支嵌套和业务复杂度。不按行数、固定层数或形式对称判断优劣，也不为了整齐而拆更多函数。

## 归属与结果

输出主流程与函数的对应关系、阻碍逐层理解的具体位置、建议的职责组织和调用顺序。局部函数类型/薄包装是否必要归 abstraction-review；字段生命周期归 data-model-review；具体故障归 code-risk-review。

## 执行与输出

用户指定范围优先；未指定时先审暂存区，为空再审工作区和相关未跟踪文件。分支比较使用实际基准的 merge-base。仅报告范围内改动引入或放大的问题，必要时追踪上下游。

每项写清：文件/行号、问题、证据、影响、建议。建议追求约束下的最优设计，明确需要调整的调用点及取舍。已证实故障与设计建议分开，未知条件标为待确认。无发现就说明；默认只审查，明确要求修复后才修改。
