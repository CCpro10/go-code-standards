# 主链路与分层 Review

## 第一原则：代码像一本可逐层阅读的书

上层像目录，说明完整流程；下层像章节，自然展开已知步骤。每深入一层增加细节和理解价值。开发者应能在任意一层停下来，解释该层完整职责、主要步骤与控制关系。

## 检查

- 从受影响入口画出真实调用链：目标、准备、执行、收尾、数据输入输出、关键分支和副作用。
- 上层不必暴露实现细节，但必须看得见业务步骤与执行顺序；下层不能突然引入名字未表达的新业务阶段。
- 同层保持相近抽象粒度，避免业务编排 → 底层操作 → 业务编排反复跳跃。
- 按自然业务职责组织流程。检查在线正常路径是否被回放、评测、后台处理等独立场景的编排侵入。
- 参数校验和失败快速返回，保持正常路径顺序清晰；重试、回滚、取消、并发与汇合的位置应可追踪。
- 区分调用深度、分支嵌套和业务复杂度。不按行数、固定层数或形式对称判断优劣，也不为了整齐而拆更多函数。

## 归属与结果

输出主流程与函数的对应关系、阻碍逐层理解的具体位置、建议的职责组织和调用顺序。局部函数类型/薄包装是否存在归 abstraction-review；字段生命周期归 data-model-review；具体故障归 code-risk-review。

## 执行与输出

用户指定范围优先；否则查看暂存区、工作区及相关未跟踪源文件，分支比较确认实际基准并使用 merge-base。说明审查范围，读取必要上下游，报告有证据的问题。默认只 Review；用户明确要求修复时才修改。提出业务约束下的最优方案，说明影响范围与兼容、性能、迁移取舍，不以最小 diff 为目标。输出位置、具体问题、证据、影响、建议与验证缺口；风险用 P1/P2/P3，个人设计约定不能直接升级为线上故障。无发现就明确说明。
