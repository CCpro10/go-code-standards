# 主链路与抽象层级 Review

## 第一核心原则：代码应该像一本可以逐层阅读的书

上层函数像目录，让人一眼看懂完整流程；下层函数像章节，解释某个步骤如何完成。每深入一层，增加的是细节，而不是理解负担。

1. 上层提供完整流程概览：不进入子函数，也能理解目标、主要步骤及其关系。
2. 下层自然展开上层步骤：进入子函数是理解已知步骤如何完成，不应突然发现新的业务流程或意料之外的职责。
3. 每层自洽：提供符合当前抽象粒度的完整解释，无需拼凑大量底层实现。
4. 抽象逐层细化：避免业务编排、底层操作、业务编排反复跳跃。
5. 每层增加理解价值：只有转发、包装且没有独立职责或边界价值的层，应审视其必要性。

**首要判断标准：开发者能否在任意一层停下来，准确解释这一层的完整职责和流程；只有想了解某个步骤如何实现时，才需要继续向下阅读。**

开始审查前读取 [完整专项规则](references/review-rules.md)。以上原则贯穿所有检查与最终评价，不能只在总结时提及。

## 执行

1. 用户指定的提交、分支或文件优先；否则先审暂存区，为空时审工作区与相关未跟踪源文件。分支审查使用实际基准分支的 merge-base，说明采用的范围。
2. 从受影响的主要入口沿真实调用链建立流程概览：目标、业务阶段、顺序、数据与控制关系、关键分支、提前结束、异常路径、输出与副作用。
3. 先看顶层是否像流程目录，再逐层阅读关键步骤。对每层执行“停下来”检查：能否独立说清职责、步骤和关键控制关系；下层是否解释预期的 How，是否隐藏新业务阶段或副作用。
4. 检查同层抽象粒度、职责内聚、函数边界、逻辑绕行、连续转发和控制流分散。区分调用深度、控制流嵌套和业务复杂度，不能仅凭名称、行数或层数下结论。
5. 保持关键失败条件、业务分支、并发执行及汇合位置可理解。尊重事务、重试、资源管理、测试隔离等真实边界，不机械压平层级。
6. 仅提出有实现和调用方证据的最小改进：重组步骤、调整职责、下沉细节或合并无意义转发。只 Review，不修改业务代码，不为形式整齐增加抽象。

## 输出

- 主链路概览：简洁流程与主要函数对应的业务步骤，必要时展开关键子流程。
- 层级评价：优先回答“能否在任意一层停下来理解完整职责与流程”，再说明顶层清晰度、同层粒度、逐层展开、职责边界和调用结构。
- 具体问题：`[P1/P2/P3] 标题`，包含文件/函数/行号、实际调用链或控制流、具体缺陷及证据、理解成本或隐藏行为的影响、最小调整建议与权衡。P1 必须有实际控制流或副作用风险证据；P2 为明显的层级、职责或主链路问题；P3 为有实际收益的小规模可读性优化。
- 最终评价：是否支持不同抽象深度的完整心智模型，是否自然对应业务流程，以及是否存在多余层级或跳转。无充分依据的问题时明确说明，不强行建议重构。

仅关注本次修改引入或放大的流程与抽象问题，不做通用格式检查，不将个人命名或函数长度偏好视为缺陷。
