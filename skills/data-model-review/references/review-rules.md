# 数据模型与数据流转专项 Code Review

## 一、核心原则

对当前代码修改进行专项 Review，重点审查数据模型的必要性、数据容器的生命周期、数据的权威来源（Single Source of Truth）以及整个业务流程的数据流转是否清晰。

遵循三个核心原则：

1. **如无必要，勿增实体**：不引入缺乏独立语义或实际价值的数据容器。
2. **Single Source of Truth（单一事实来源）**：同一业务事实应尽可能只有一个明确的权威数据来源，避免多份可变副本及同步问题。
3. **长期对象优先**：优先审查贯穿业务生命周期的结构体、Context 和其他长期存活的数据容器，而不是只关注局部变量的表面精简。

**Review 的最终目标不是让结构体、变量或字段数量最少，而是用最少的必要数据概念、最清晰的数据所有权与生命周期，表达完整的业务流程。**

## 二、Review 范围

关注所有能够承载、定义或持久化数据的实体，包括但不限于：

- Struct、Class、DTO、Request、Response、Task、Context、Result
- 结构体字段、成员变量、局部变量、函数参数、临时对象
- Map、List、Tuple、集合及中间数据容器
- 常量、枚举、配置及状态字段
- API / IDL / Protobuf / Schema 的定义
- 数据库表、字段、索引、关联关系与持久化模型

不要将 Review 限制在 Diff 内部，应结合必要的上下游调用链，理解数据的完整生命周期。但最终发现的问题应聚焦本次修改引入或明显放大的设计问题。

---

## 三、最高优先级：长期对象与数据生命周期

**这是本次 Review 最重要的检查之一。**

重点关注那些生命周期长、跨多个函数或模块传递、参与多个处理阶段的数据结构。

例如：

- RequestContext / TaskContext / ProcessContext
- Request / Task / Result 等核心业务结构体
- 在请求切分、任务调度、处理执行、结果聚合等阶段反复传递的对象
- 长期持有状态的管理器、缓存、共享对象

一个典型的数据流程可能是：

`Request → Context → Task → Worker → Result → Response`

需要沿着实际代码追踪这些数据容器，而不是只看它们的定义。

### 3.1 审查长期结构体的每一个字段

对于关键的长期对象，尽可能弄清楚：

1. 字段从哪里产生？为什么需要它？
2. 字段在哪个阶段初始化？
3. 哪些函数读取它？哪些函数修改它？
4. 字段是否真的需要贯穿整个生命周期？
5. 最后一次使用发生在哪里？
6. 能否缩短它的生命周期，改为局部变量或阶段性数据？
7. 是否能够直接从已有权威数据来源获取，而不必保存？
8. 是否和其他结构体中的字段表示同一份事实？

**特别警惕：一个 Context 不断添加字段，逐渐成为所有处理阶段的公共数据仓库。**

例如：

一个字段只在任务切分阶段使用，但被放进贯穿整个请求处理流程的 Context 中；另一个字段只在结果聚合时需要，却在请求初始化阶段就被创建和保存。

这种设计会增加长期对象的状态空间，也会让开发者难以判断哪些字段在什么阶段有效。

应该考虑将阶段性数据限制在其实际需要的生命周期内。

### 3.2 审查长期对象是否过度承担职责

检查是否存在：

- Context 承载了过多阶段性、临时性的数据
- 核心结构体中存在大量仅被少数函数使用的字段
- 不同处理阶段不断为同一个结构体添加字段
- 字段有效性依赖隐含的处理阶段或执行顺序
- 已经失效的数据仍长期留在对象中
- 为方便传参而将不相关的数据全部塞进一个结构体
- 多个阶段共同修改同一个对象，导致状态所有权不清晰

尤其要关注：

**一个长期存活的数据容器是否真的需要持有这么多数据，还是仅仅因为它容易被传递，所以逐渐承载了越来越多不相关的状态？**

但不要机械拆分 Context。若拆分会引入复杂参数传递、破坏封装或增加状态同步，应综合判断实际收益。

## 四、最高优先级：Single Source of Truth

**这是本次 Review 另一个最重要的检查。**

核心要求：

**对于每一项重要的业务事实，应当能够明确回答：哪一份数据才是它的权威来源？**

重点审查同一业务数据在多个结构体或处理阶段之间重复出现的情况。

例如：

`Request → Task → Context → Result`

同一个字段可能同时存在于 Request、Task、Context 和 Result 中。

需要判断：

- 是否真的需要在四个结构体中分别保存？
- 哪一个字段才是权威来源？
- 其他字段是必要的快照、转换结果，还是单纯复制？
- 数据修改后，其他副本是否需要同步？
- 如果副本不一致，业务应该相信哪一份？
- 是否可以通过引用、复用现有数据或直接传递来减少重复状态？

### 4.1 特别识别重复状态

优先发现以下问题：

**同一事实多份保存**

相同业务信息在多个对象中独立保存，且没有明确必要性。

**原始值与派生值同时持久保存**

某字段可以从其他字段可靠、低成本地计算出来，却被作为独立可变状态维护。

**数据复制后的同步依赖**

修改 A 字段时必须同时修改 B 字段，否则业务会出现不一致。

**多处更新同一业务事实**

不同模块分别维护同一事实，导致不存在明确的数据所有者。

**不必要的模型间转换**

多个结构体字段几乎完全相同，只是在不同处理阶段反复复制、包装和解包。

### 4.2 对每份重复数据追问

1. 这份副本为什么必须存在？
2. 它是否具有独立业务语义？
3. 是否存在更权威的原始数据？
4. 它是不可变快照、缓存、派生表示，还是另一份可变状态？
5. 如果移除它，是否可以减少字段同步和状态维护？
6. 如果必须保留，是否明确规定了数据所有者、生成时机、失效条件和一致性约束？

**不要将所有重复表示都视为错误。**

合理的重复可能来自：

- 必要的不可变快照与时间点隔离
- API / IDL 与内部模型的边界隔离
- 性能优化、缓存和数据库反规范化
- 并发隔离、数据所有权与安全需求
- 协议兼容、审计记录及历史数据保留

但这些重复应当具有明确理由，而不是无意识地复制数据。

判断重点不是字段是否同名，而是**它们是否表达相同的业务事实，以及是否产生了不必要的多份权威状态**。

## 五、审查整个数据流转路径

不要只对单个结构体进行局部 Review。

应当先识别本次修改涉及的主要数据流，例如：

`IDL Request → 参数解析 → Context → 请求切分 → Task → 执行 → Result → 聚合 → IDL Response / DB`

然后重点检查：

- 数据是否发生不必要的复制、转换或重新包装？
- 是否存在没有独立语义的中间数据结构？
- 是否能减少数据在多个模型之间反复搬运？
- 是否存在为了适配某个临时实现而新增的数据字段？
- 同一字段是否在不同处理阶段被赋予不同含义？
- 生产者、消费者、所有者和修改者是否明确？
- 能否在不破坏模块边界的前提下，让数据从生产者更直接地到达消费者？

**优先优化数据流转路径，而不是单纯减少代码行数。**

一个结构体看起来可能非常简单，但如果为了生成它需要经过三次复制、两次转换，并且引入额外状态同步，就可能是不合理的设计。

反过来，一个独立结构体虽然增加了定义数量，但如果它能明确区分业务阶段、隔离可变状态或减少隐式耦合，也可能是合理的。

## 六、其他数据容器与定义的合理性

在完成长期对象和 Single Source of Truth 的重点检查后，再审查其他数据设计。

### 6.1 局部变量、临时对象、常量

检查：

- 是否存在没有必要的中间变量或临时容器？
- 是否有仅为了转发数据而增加的包装对象？
- 是否重复定义相同语义的常量、枚举或配置？
- 是否存在没有必要的状态缓存或重复计算结果存储？
- 是否存在没有实际收益的局部数据复制？

局部变量能够提升语义清晰度时应当保留，不要追求机械内联。

### 6.2 IDL / API 定义

重点关注：

- Request / Response 是否包含冗余字段？
- 是否存在多个字段表达相同业务信息？
- 是否出现不必要的层层嵌套和包装？
- IDL 模型与内部模型之间是否存在无意义的重复转换？
- 字段的可选性、默认值、语义和生命周期是否清晰？
- 是否存在同一业务事实在接口与内部状态中被分别维护的问题？

注意协议兼容性，不要为了简化数据模型而破坏现有客户端。

### 6.3 数据库设计

检查：

- 表、字段及关联关系是否必要？
- 是否存储了可直接推导的数据？
- 是否存在多个地方维护相同业务状态？
- 是否有冗余字段需要额外同步却缺乏一致性保障？
- 数据库模型与内部业务模型之间是否存在多余转换？
- 是否有必要的索引、缓存、反规范化或历史快照需求？

必须综合考虑查询性能、事务一致性、兼容性及数据迁移成本。

## 七、Review 执行顺序

请按照以下顺序执行，避免把注意力分散到低价值的细节上。

**第一步：理解数据主链路**

阅读 Diff 和必要上下游代码，梳理本次修改中核心数据的产生、传递、修改与消费。

**第二步：识别长期对象**

列出关键的长期结构体、Context 和跨阶段共享的数据容器，分析其生命周期及字段必要性。

**第三步：寻找重复事实来源**

检查相同业务事实是否出现在 Request、Context、Task、Result、IDL、数据库等多个位置，确定其权威来源和重复表示的必要性。

**第四步：寻找冗余流转**

检查不必要的中间对象、数据转换、复制、状态缓存和字段同步。

**第五步：检查边界设计**

审查 IDL、数据库、局部变量、常量等是否合理，同时确认性能、兼容性和模块边界约束。

**第六步：提出最小改进**

优先选择能够删除重复状态、缩短数据生命周期、明确权威来源或减少不必要转换的方案。

不要为了减少结构体数量而引入更难理解的代码。

## 八、Review 输出格式

### 1. 核心数据流转概览

简要描述本次修改涉及的数据流：

- 数据从哪里产生？
- 经过哪些核心数据容器？
- 在哪里发生转换或修改？
- 最终由谁消费或持久化？

### 2. 长期对象专项结论

明确指出：

- 哪些对象跨越较长生命周期？
- 字段职责和存活范围是否合理？
- 是否存在长期保存的临时状态？
- 是否存在过度膨胀的 Context 或核心结构体？
- 是否存在值得收缩生命周期或删除的字段？

### 3. Single Source of Truth 专项结论

明确指出：

- 关键业务事实的权威来源是否清晰？
- 是否存在多个可变副本？
- 是否有不必要的数据复制或重复存储？
- 是否存在数据同步和状态不一致风险？
- 是否有合理但需要说明的重复表示？

### 4. 具体问题

仅输出有充分依据、实际值得修改的问题。

每个问题包含：

**[P1/P2/P3] 问题标题**

- **位置**：文件路径、行号、结构体或字段
- **问题**：具体的数据设计缺陷
- **证据**：引用相关读写位置及上下游流转关系
- **影响**：对数据一致性、生命周期、维护复杂度或性能的影响
- **建议**：最小且可执行的修改方案，以及相关权衡

优先级定义：

- **P1**：存在状态不一致、数据错误、兼容性风险或明显性能损失
- **P2**：明确的重复事实来源、冗余长期状态、不合理生命周期或多余数据流转
- **P3**：有实际收益但影响较小的数据设计优化

### 5. 总体结论

最终回答三个问题：

1. **长期数据容器是否足够精简，字段生命周期是否合理？**
2. **核心业务数据是否具有明确的 Single Source of Truth？**
3. **整个业务流程的数据流转是否直接、清晰且没有不必要的中间状态？**

如果没有发现有充分依据的问题，直接说明数据设计合理，不必强行提出优化建议。

## 九、Review 约束

- 这是**数据设计与数据流转专项 Review**，不是通用代码风格检查。
- **长期对象与 Single Source of Truth 的优先级高于局部变量精简。**
- 不能只依据结构体定义下结论，必须结合实际字段读写和调用链。
- 不把必要的领域模型、接口隔离或不可变快照误判为冗余。
- 不将“结构体更少、代码行数更短”直接等同于设计更好。
- 不做没有证据的推测，不提出纯个人风格偏好。
- 重点关注当前修改引入或放大的问题。
- 只进行 Review，不直接修改代码。

**最终目标：让核心业务事实有明确的权威来源，让每份数据只在真正需要的时间和范围内存在，让整个数据生命周期能够被清晰地理解和追踪。**
