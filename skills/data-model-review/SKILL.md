# 数据模型与数据流转 Review

## 核心原则

- 如无必要，勿增实体：每个数据容器都应有独立语义或实际价值。
- 单一事实来源（Single Source of Truth）：每项重要业务事实有明确权威来源，避免多份可变副本和隐含同步。
- 长期对象优先：先审跨阶段的结构体、Context 和共享状态，再看局部变量精简。
- 最优设计优先：在业务约束下追求清晰、完整且长期可维护的数据模型，不以修改行数或文件数量最少为目标。

目标是用必要的数据概念、清晰的所有权和生命周期表达完整业务流程，而非机械减少结构体、字段或代码行数。只 Review，不直接修改代码。

## 审查顺序

1. **确定范围与主链路。** 用户指定的提交、分支或文件优先；否则先看暂存区，为空时看工作区与相关未跟踪源文件。分支比较使用实际基准的 merge-base。说明范围，并沿必要上下游追踪数据的产生、传递、修改、转换、消费和持久化，不仅凭结构体定义下结论。
2. **审查长期对象。** 对跨阶段的 Request、Context、Task、Result、管理器和共享对象，逐字段确认来源、用途、初始化阶段、读写者、所有者与最后使用位置。检查临时状态长期保存、失效字段残留、字段有效性依赖隐含执行顺序，以及 Context 为方便传参而不断膨胀的问题；判断能否改成局部或阶段性数据。
3. **确定权威来源。** 对 Request、Task、Context、Result、IDL、数据库中的同一业务事实，区分原始值、派生值、快照、缓存和可变副本。重点检查低成本可推导字段被独立维护、修改 A 必须同步 B、多模块各自更新同一事实；必要副本应明确所有者、生成时机、失效条件和一致性约束。
4. **检查冗余流转。** 沿主链路寻找没有独立语义的中间容器、同形模型的反复复制/包装/解包、为临时实现新增的字段，以及同一字段在不同阶段含义变化。让数据在保留必要模块边界的前提下，更直接地从生产者到达消费者。
5. **检查边界与持久化。** IDL/API 关注冗余字段、重复语义、嵌套包装、可选性和默认值。数据库关注表、字段、关联、索引、派生数据与重复状态维护。最后检查局部临时对象、常量和枚举的重复定义。综合查询性能、事务一致性、协议兼容与迁移成本判断必要性。
6. **提出最优改进。** 从完整数据链路出发，删除无独立价值的冗余字段、重复状态和中间容器，收敛权威来源、缩短不必要的生命周期、消除无效转换及同步依赖。必要时建议连同相关模型和上下游读写点一起调整，不能因追求小 diff 而保留设计冗余或只做局部修补。以本次修改引入或明显放大的问题为切入点，用字段读写与调用链证据支撑方案，说明兼容、性能和迁移约束下的取舍。

## 判断边界

- 不同名也可能表达同一事实，同名也可能具有不同业务语义；不能仅按字段名称判断重复。
- 不可变快照、时间点隔离、缓存、反规范化、并发/安全隔离、协议适配与审计历史可以合理保留，但要有明确理由。
- 不机械拆分 Context、合并边界模型或内联局部变量；如果调整会破坏封装、增加参数传递或状态同步成本，应说明权衡。
- 聚焦数据设计与流转，不报告通用命名/格式偏好或无关历史问题，不凭猜测强行提出优化。

## 输出

1. 简述核心数据流、长期对象与权威来源，包括必要的重复表示。
2. 具体问题按优先级排序：`[P1/P2/P3] 标题`，给出文件/行号与对象或字段、设计缺陷、上下游读写证据、影响、推荐的最优改进方案及权衡。明确应删除、合并或调整的字段、容器和读写点。P1 为实际一致性、数据、兼容或明显性能风险；P2 为明确的重复事实来源、冗余长期状态、不合理生命周期或流转；P3 为有实际收益但影响较小的优化，优先级不按改动量划分。
3. 总体回答：字段生命周期是否合理，核心事实来源是否明确，数据流转是否直接清晰。没有充分依据的问题时明确说明，不强行提出建议。
