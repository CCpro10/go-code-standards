# 契约与失败边界 Review

## 核心判断

调用方保证前置条件，被调方保证后置条件。不可信数据在明确入口解析校验，核心流程依赖已建立的契约。

## 检查

- 标出输入可信边界、字段来源、必填性、验证责任与错误传播路径。缺少契约时先记录未知，不猜测合法值。
- 业务字段如 occurred_at 必须显式传入；禁止 service 静默用 time.Now() 补齐。业务配置缺失应暴露；默认值仅限明确工程参数或有文档的兼容行为，并放在入口。
- 内部固定 timeout/poll interval 不应层层 normalize、截断或补默认值；启动、配置加载或构造期确定并校验。
- 依赖缺失、构造参数错误尽早失败，不让每个 RPC 用 not implemented 等分支兜底。
- 检查 trim、过滤空字段、偷偷去重、混合解析来源是否掩盖非法输入。契约明确要求的规范化可以保留，但要说明作用边界。
- 被调函数应在无法满足后置条件时返回错误；调用者不要重复猜测 nil 结果或合法状态。真正外部信任边界仍需校验。
- 检查吞掉错误、只记录却继续成功、错误回退到默认对象，以及未明确设计的降级。错误责任和恢复语义应清晰。

## 归属

审查“谁负责保证条件，失败如何显露”。数据所有权归 data-model-review；函数包装必要性归 abstraction-review。已有具体请求路径证明数据错误、panic、重复执行等故障时由 code-risk-review 主报，本专项补充契约证据。

## 执行与输出

用户指定范围优先；未指定时先审暂存区，为空再审工作区和相关未跟踪文件。分支比较使用实际基准的 merge-base。仅报告范围内改动引入或放大的问题，必要时追踪上下游。

每项写清：文件/行号、问题、证据、影响、建议。建议追求约束下的最优设计，明确需要调整的调用点及取舍。已证实故障与设计建议分开，未知条件标为待确认。无发现就说明；默认只审查，明确要求修复后才修改。
