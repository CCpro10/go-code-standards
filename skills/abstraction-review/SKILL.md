# 行为抽象必要性 Review

## 核心判断

每层行为抽象都应说明：隔离什么契约、隐藏什么复杂度，或支持什么实际变化。调用目标固定时，优先具体类型与直接调用。

## 检查

- 搜索具名函数类型、函数类型字段/参数/返回值、函数值赋值及业务动作集合，例如 `type Runner func(...)`、`Finish func(...)`、`f := service.Execute`。追踪赋值点、实际实现与调用方；未查全时不要断言只有一个实现。
- 回答：有几个实际实现？行为是否需要运行时变化？直接调用后是否更清楚？不要为了预想的第二实现、测试注入或少量重复引入接口/策略。
- 业务层通常禁止函数值层层传递；去掉类型名改成匿名签名不能解决问题。标准库、框架必要回调限定在实际技术边界，解释必要性。
- 禁止函数别名、无意义常量别名及重复职责的薄包装。`GenerateWithArk → GenerateWithArkModel` 仅多了读配置、trim、默认值，不足以证明多一层的价值。
- 不为单次简单逻辑抽 helper；有业务意义、确实降低复杂度或真实复用时才抽取。不要机械替换成更多接口、策略结构体或转发函数。
- 给出应删除/合并的抽象、直接调用路径及所有受影响调用点。保留真正外部适配契约；具体领域数据类型不因“只有一种”而被删除。

## 归属

只回答“这层抽象是否必要”。整体流程编排归 main-flow-review；数据字段/状态生命周期归 data-model-review；默认值的合法性归 contract-boundary-review。证明具体故障的同根因问题优先归 code-risk-review，不重复报。

## 执行与输出

用户指定范围优先；未指定时先审暂存区，为空再审工作区和相关未跟踪文件。分支比较使用实际基准的 merge-base。仅报告范围内改动引入或放大的问题，必要时追踪上下游。

每项写清：文件/行号、问题、证据、影响、建议。建议追求约束下的最优设计，明确需要调整的调用点及取舍。已证实故障与设计建议分开，未知条件标为待确认。无发现就说明；默认只审查，明确要求修复后才修改。
