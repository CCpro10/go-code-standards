# 多专项 Review 总入口

## 确认审查设置

先只读检查仓库，再集中确认三项设置：

1. 范围：仓库/worktree、分支和基准提交，或暂存区/工作区；是否包含未跟踪文件和未提交修改。
2. 专项：Go 表达规范、行为抽象、主链路分层、数据模型、契约边界、正确性风险。可全选或选择子集；给出根据 diff 的建议。
3. 子 Agent 的模型和思考等级：可以统一设置，也可分专项指定。查询当前可用的子 Agent 工具能力，不编造模型名或参数。

已在当前请求明确的选项只回显、不重复询问。未明确的设置必须等用户回答后再启动；可以先只读收集 diff 和项目约定。用户明确授权“你决定”时自行选择并说明。模型不可用时告知并请用户选择，不静默替换。

## 调度

- 固定基准与源提交，保存本次选定 diff 和相关未跟踪文件快照；读取项目约定和需求依据。需求不明时标记不能验证的部分。
- 每个选中的专项分别创建一个独立子 Agent，最多六个：go-code-standards（中文权威规则已内置）、abstraction-review、main-flow-review、data-model-review、contract-boundary-review、code-risk-review。
- 使用独立上下文，不 fork 整段历史。传入明确仓库路径、固定 diff/提交、必要需求、约定、该专项 Skill 及其必读引用规则、归属边界与只读要求。工作区发生变化时，受影响的专项须基于新快照重审；不混用不同版本结论。
- 按用户确认的模型和思考等级设置工具实际支持的参数。子 Agent 不再派生其他子 Agent，不修改代码、不提交、不推送；缺少工具能力时明确说明，等待选择替代方式。
- 等待全部选中专项完成，记录失败或未覆盖项。主 Agent 逐条核验读写位置与触发条件，删除弱证据结论，核对需求是否遗漏或实现越界。

## 汇总与归属

同根因只主报一次。实际故障归风险；责任/校验/默认值归契约；数据状态与所有权归模型；整体编排归主链路；行为间接层归抽象；局部表达归 Go 规范。其他专项补充证据，不重复计数。

输出：范围与版本；每个专项的模型/等级及完成、失败或未覆盖状态；去重问题（位置、证据、影响、建议）；需求符合性和验证缺口。建议追求约束下的最优方案，不以最小 diff 为目标。默认只 Review；用户要求修复时，再由主 Agent 综合执行和验证。

git-review-mode 只负责 GoLand 审查现场准备；除非用户要求，不在 Review 中切分支或改变暂存区。
