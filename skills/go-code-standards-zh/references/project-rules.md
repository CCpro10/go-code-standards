# Go 风格与可维护性规则

本文件是 Go style Skill 的最高优先级规则，必须完全遵守。它只处理风格、可读性和可维护性问题，默认代码逻辑是正确的。

不要用本 Skill 查并发问题、可疑 bug、性能问题或业务逻辑错误；这些风险项交给 `code-risk-review`。

## 优先级

1. 本文件规则：最高优先级。
2. `references/go-style-rules.md`：来自 Google Go Style 和 Uber Go Style Guide 的通用 Go 风格规则。
3. 仓库本地约定：不违反前两类规则时遵守。

## 目录和 Package

- 目录层级应表达业务模块和职责边界，不要按临时实现细节、工具函数或过深技术分层切目录。
- package 名称要短、小写、有意义；避免 `util`、`common`、`misc` 这类无法表达职责的名字。
- 拆文件、迁移目录、拆 package 属于较重的结构调整。审查时可以指出文件职责不聚焦、同一文件承载过多主题、建议按哪些职责拆分，但不要主动执行拆文件或移动代码；必须等用户明确确认后再做。
- 一个 package 内最重要的可导出函数和方法放在最前面，其次是其他可导出函数和方法，最后是不可导出函数和方法。
- 将第一个不可导出函数或方法视为 private section 的开始；其后不要再放大写开头的函数或方法。
- 禁止把非 API 函数标注为可导出。不能为了跨文件调用、测试方便或看起来重要而大写开头。

## 数据结构和契约设计

- 数据结构决定核心实现。审查时必须先明确业务不变量、读写路径和状态生命周期，再按 IDL、DB schema、核心结构体、函数实现的顺序检查；不要用复杂业务代码弥补错误或含糊的数据模型。
- IDL 必须准确表达稳定接口契约。检查字段名称和类型、必填与可选语义、默认值来源、单位、时间格式、ID 类型、枚举取值、错误模型以及向前/向后兼容；禁止用模糊字符串、通用 map、可空字段或透传 payload 掩盖本应明确的业务概念。
- DB schema 必须围绕真实访问方式和数据不变量设计。检查主键和业务唯一键、字段类型、空值与默认值、约束、索引、状态字段、时间字段、数据所有权、生命周期及迁移兼容性；不要把本可由 schema 保证的一致性长期留给每个调用方维护。
- 核心结构体必须表达稳定领域概念，而不是机械复制 IDL、数据库行或临时调用参数。字段应有明确语义、来源、所有权、单位、有效范围和生命周期；避免重复存储同一事实、互相矛盾的状态字段和无法判断合法组合的大型 option bag。
- IDL、数据库模型和领域结构体可以不同，但每层存在都必须有明确边界价值。语义完全相同时优先复用，语义或生命周期不同时显式转换；禁止无理由逐层复制同形结构，也禁止为了少写转换代码把传输层或持久层类型泄漏到全部业务逻辑。
- 设计必须判断长期演进成本和当前场景的最佳实践：新增字段或状态后是否仍能保持不变量，兼容升级是否明确，调用方是否需要重复猜测语义，迁移和排错是否可控。不要只以“当前能跑”作为设计通过标准。
- 提出“最佳实践”结论时必须结合当前业务约束、读写模式和兼容要求说明理由；不要脱离场景机械套用范式。

## 结构体

- 结构体必须必要、清晰，并且降低理解成本。禁止为了中间转换、临时拼装或掩盖调用链而定义大量中间结构体。
- 定义结构体前先确认它是否表达稳定业务概念、外部契约、持久状态或多处复用的数据形状。
- 如果只是单次传递几个字段、临时组装参数或给后续覆盖使用，优先使用明确输入、局部变量或直接构造目标对象。
- 字段含义、来源和生命周期必须清楚；看不出边界的结构体不要定义。
- 所有可导出的结构体必须有详细注释，说明它代表的业务概念、用途、边界、生命周期或外部契约。
- 可导出结构体里的字段必须有清晰注释，说明字段含义、来源、单位、边界或使用限制。
- 非 API 结构体禁止用大写开头标成可导出；不能为了跨文件使用、测试方便或看起来重要而导出结构体。

## 函数和方法

- 函数和方法的划分必须合理。方法应表达接收者的行为或状态变化；如果和接收者没有真实关系，优先使用普通函数。
- 函数应先处理异常路径并快速返回，再处理正常逻辑。参数为空、输入非法、依赖缺失、`err != nil` 等失败条件应放在主流程之前，避免用多层嵌套包住正常业务逻辑。
- 好代码优先短而直。能用少量顺序代码表达清楚的逻辑，不要拆成大量单次使用的小函数。
- 不要为了只使用一次的逻辑额外抽小函数。只有当函数能降低复杂度、表达明确业务概念或被多处复用时才抽出来。
- 不要把代码切成过多小函数；可以提出按职责拆文件的建议，但在用户确认前不要主动拆文件或移动代码。
- 禁止无语义的纯转发函数，例如只把参数原样传给另一个函数并直接返回结果的 `parsePositiveIDStringParam` 这类单函数套壳。没有新增业务语义、边界校验、错误上下文或接口适配时，必须内联调用被包装函数，或直接重命名底层函数；不要为了“名字看起来更具体”而多包一层。
- 通常不要把函数作为参数传递，只为一次性逻辑制造 callback、strategy 或 handler 抽象。调用目标固定时直接调用，让执行顺序和调用链在函数体内可见；只有接口契约本身要求回调、确有多个行为实现，或边界注入能明显降低复杂度时才使用函数参数。
- 禁止通过 `var` 声明函数别名，包括 `var afunc = packageb.Bfunc`、`var afunc = bfunc` 和显式函数类型的等价写法。直接调用原函数；不要通过换名缩短调用、隐藏来源、伪造新的语义层或用可变包级函数做测试替换。
- 函数代码必须包含有信息量的注释。简单函数说明业务意图、输入边界或返回语义；复杂函数说明关键分支、状态变化或业务约束。
- 函数注释应面向实际执行过程，说明关键步骤的先后顺序、选择条件和未命中后的下一步；不要只写“按某种策略处理”这类抽象概括，让读者仍需进入函数体才能知道具体行为。
- 反例：`// resolveSpecifiedTitle 按自定义创作优先级解析两个入口的指定歌名。`
- 正例：`// resolveSpecifiedTitle 先尝试解析高级创作的标题；如果没有解析出，再使用灵感创作的标题。`
- 注释不能只复述代码，不写“给变量赋值”“调用方法”这类无信息量注释。

## 局部可读性

- 变量尽量延后声明。如果一个变量可能因为后续步骤失败而没有机会使用，就把声明放到失败点之后。
- 空结构体和 nil 返回值优先显式直接返回。例如失败时返回 `dailyLoginRewardConfig{}`，不要提前声明空变量只为失败路径复用。
- 大业务结构体优先使用 keyed composite literal 一次性构造，让完整对象形状集中出现在一个地方。
- 不要先声明空结构体再逐字段赋值，除非 API 或控制流确实要求可变赋值。
- 使用合理空行和换行表达逻辑阶段，让代码一眼能看出主流程。

## 命名和边界表达

- 函数名必须清晰，并与函数实际完成的功能准确对应。读者应能从名字判断它处理什么对象、执行什么动作以及返回什么结果或产生什么影响；名字不能只描述其中一步、理想路径或抽象目的。
- 实现职责变化时必须同步检查函数名。函数如果同时执行解析、过滤、去重、补默认值或产生副作用，名称必须完整反映这些真实行为；否则应收窄职责或使用更准确的名字，不能保留误导性旧名称。
- 命名应在不损失原意的前提下尽量简洁，不能为了完整而机械堆叠单词，也不能为了简短而省略对象类型、键值关系、单位、范围或状态等关键信息。选择能够完整、无歧义表达业务语义的较短名称。
- 可以使用团队和 Go 代码中含义稳定、无需猜测的常用缩写，例如 `ID`、`URL`、`Req`、`Resp`、`Config`、`Ctx`。例如 `newInterruptSessionResponse` 过长，应写成 `newInterruptSessionResp`。禁止为了缩短长度创造生僻缩写，或在同一 package 内对同一个词混用多种缩写。
- slice、array 或其他 list 语义变量必须使用“具体元素业务类型的复数”命名，例如 `userIDs`、`orders`、`skillRefs`。禁止使用 `list`、`slice`、`array`、`arr`、`items`、`values`、`data`、`result` 等无法说明元素业务含义的名字。
- map 变量必须使用 `<key>2<value>` 命名并明确键和值的业务含义，例如 `userID2user`、`skillKey2version`、`scene2config`。禁止使用 `mapping`、`lookup`、`cache`、`data` 或只表达键/值一侧的名字。
- 避免 `handleXxx`、`processXxx`、`doXxx`、`runXxx` 等无法说明具体行为的泛化命名，除非所在接口或上下文已经让职责完全明确。
- 命名必须让读者知道函数真实做了什么。避免用 `normalizeXxx` 隐藏 trim、过滤、去重、默认值补齐和数据重塑等多种行为。
- 如果确实需要转换、去重、解析或校验，函数名应明确表达真实动作，例如 `parseXxx`、`dedupeXxx`、`validateXxx`。
- 禁止无意义常量别名，例如 `taskQueryStatePending = SongResultStatePending`。如果两个名字表达的是同一个状态、同一个枚举值或同一个业务概念，直接使用原常量；不要为了局部命名、调用方便或看起来分层而重新起一个等值常量。
- 业务对象应从明确输入构造出来，不要先构造“默认业务对象”，再在分支里覆盖成另一种语义。
- 禁止在业务流程里对内部工程参数做无意义兜底或归一化，例如 `normalizeAudioParseSyncTimeout` 这类把非用户输入的 timeout、poll interval、retry limit 静默改成默认值或最大值的函数。内部配置应在构造期、启动期或配置加载入口一次性确定并校验；如果代码内部传错了非法值，应暴露为清晰错误或直接修正调用点，而不是在每条执行链里继续兜底。
- 默认值只允许出现在明确入口：外部请求解析、配置加载、兼容协议适配或构造函数。默认来源、适用范围和边界必须一眼可见；不要把默认值藏在深层 helper、service 方法或循环调用路径里。

## 指针 Helper

- 不要手写 `stringPtr`、`int64Ptr`、`boolPtr` 这类指针 helper；统一使用 `code.byted.org/lang/gg/gptr` 的 `gptr.Of(...)`。
- 常量数字传给 `gptr.Of` 时注意类型推断；需要 `*int64`、`*int32` 等明确类型时使用 `gptr.Of[int64](...)`、`gptr.Of[int32](...)`。
